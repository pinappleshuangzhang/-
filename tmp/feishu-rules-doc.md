# 用规则驱动 AI 建站：从 0 到 1 实操教程

## 这份教程解决什么问题

用 AI 写网站，最常见的失败不是"AI 写不出代码"，而是"AI 每次写出来的都不一样"：这次用 Tailwind 默认色，下次用十六进制；这次组件放 `components/`，下次直接堆在页面里；这次动画用 CSS，下次用 GSAP。项目跑到一半，代码库变成几种风格的拼贴，改一处坏三处。

解决办法是**先写规则，再写代码**。把架构、设计令牌、性能红线、兼容要求写成规则文件，AI 每次对话都会自动读取并遵守，相当于给它一份永不失忆的项目手册。

本教程给出一套经过完整项目验证的 9 份规则，逐条解释每条规则在管什么、为什么这么定，附上可直接复制的规则文件全文，并说明在项目的前期、中期、后期分别该怎么用它们。

适用对象：用 Cursor 等 AI 编辑器开发 Next.js 网站。技术栈以 Next.js App Router + TypeScript + Tailwind + GSAP 为例，但规则思路可迁移到其他栈。

## 一、规则文件怎么生效

**存放位置**：项目根目录下新建 `.cursor/rules/` 文件夹，每份规则是一个 `.mdc` 文件。

**文件格式**：开头是 YAML 元信息，之后是 Markdown 正文。

```
---
description: 这份规则管什么，一句话说清
alwaysApply: true
---

# 规则标题

- 具体条款一
- 具体条款二
```

**关键字段**：

- `alwaysApply: true` 表示每次对话都自动加载，适合架构、令牌、性能这类全局约束。
- `alwaysApply: false` 配合 `globs: **/*.tsx` 表示只在涉及匹配文件时加载，适合特定技术栈的细节约定。规则总量大时用它节省上下文。

**写规则的三个要点**：

1. **写"禁止什么"比写"建议什么"有效**。"禁止 `any`"比"尽量用具体类型"约束力强得多。
2. **给出替代方案**。禁止一件事的同时说清该用什么，例如"禁止动 width，需要尺寸变化用 `scale` 或 clip-path"。
3. **能自动化的就别只写在规则里**。代码风格类约束同时配置 ESLint，让工具兜底，规则文件负责解释原因。

## 二、三阶段总览

| 阶段 | 目标 | 本阶段落地的规则 |
| --- | --- | --- |
| 前期（开工前） | 打地基，定下不可动摇的约定 | AI 工作流、项目架构、代码质量、设计令牌、响应式布局 |
| 中期（页面开发） | 按规范持续产出，边写边防坑 | GSAP + Lenis 集成、性能、无障碍、浏览器兼容（降级预留） |
| 后期（收敛上线） | 多端适配、性能收敛、验收 | 浏览器兼容（提测）、性能（内存收敛）、全分辨率与无障碍验收 |

一个重要提醒：**前期那五份规则必须在写第一行业务代码之前定好**。它们描述的是"整个项目长什么样"，一旦有几十个文件按旧约定写完，再改规则就要全量返工。实践中最容易犯的错，就是把响应式适配策略推迟到"以后再说"，结果后期在超宽屏适配上大规模重写。

## 三、前期：开工前必须落地的五份规则

### 规则 1：AI 工作流（ai-workflow.mdc）

**它解决什么问题**

AI 有两个典型毛病：一是不问就动手，你让它改个按钮，它顺手重构了整个组件；二是改完不验证，代码跑不起来才发现。这份规则给 AI 套上"编码前—编码中—编码后"三段流程。

**逐条解释**

- *编码前先分析现有代码*：防止 AI 凭空造一套与现有代码风格冲突的实现。
- *复杂任务先给方案*：让你在它动手前就能否决错误方向，成本远低于写完再推翻。
- *重大架构变更先征得同意*：目录调整、换核心依赖、改 Provider 层这类改动影响面大，必须人来拍板。
- *每次改动聚焦单一目标，不顺手重构*：把改动范围限制住，出问题时容易定位和回滚。
- *未经同意不装依赖*：防止为了一个小功能引入一个大包。
- *编码后跑 lint 和 build*：把"能跑"作为交付的最低标准。
- *每次改动做一次中文提交*：形成可追溯、可回滚的历史。提交信息用中文短句描述做了什么，比 "fix"、"update" 有用得多。

**规则文件全文**

```
---
description: AI 工作流程规范（编码前分析、编码中约束、编码后验证）
alwaysApply: true
---

# AI 工作流程规范

## 编码前

1. 先分析现有代码结构和相关文件，理解上下文再动手。
2. 复杂任务先给出实现方案（涉及哪些文件、怎么拆分），再开始编码。
3. 重大架构变更（目录结构调整、核心依赖替换、Provider 层改动）必须先征得同意。

## 编码中

- 小范围修改：每次改动聚焦单一目标，不顺手重构无关代码。
- 未经同意不安装新依赖；需要新包时先说明用途和理由。
- 新建组件、hook、工具函数前，先检查 `components/`、`sections/`、`hooks/`、`lib/` 是否已有可复用实现。

## 编码后

- 运行 `npm run lint`，零错误。
- 运行 `npm run build`，构建通过（Google Fonts 网络超时导致的失败可重试一次）。
- 总结本次改动：列出变更的文件及各自改了什么。
- 每次大的修改完成并验证通过后，执行一次本地 git 提交，提交信息用简短中文描述本次改动（如「还原第二屏并抽取公共组件」）。
```

**三阶段怎么用**

- 前期：第一份写的就该是它，之后所有协作都在这套流程里进行。
- 中期：严格执行"一次改动一个目标 + 一次中文提交"，历史清晰到能按提交回溯任何一个决策。
- 后期：兼容性和性能类改动，提交前额外附上验证结论（在哪些浏览器、哪些分辨率测过）。

### 规则 2：项目架构（project-architecture.mdc）

**它解决什么问题**

没有目录约定时，AI 倾向于把所有东西写进页面文件，最后出现两千行的 `page.tsx`。这份规则规定每种代码该放哪、什么时候必须拆。

**逐条解释**

- `app/` *只做组合*：页面文件只负责把区块拼起来，不写布局细节和动画。这样看一眼页面文件就知道这页由哪些部分构成。
- `sections/` *一个区块一个文件*：首屏、列表区、联系区各自独立，改一屏不会碰到另一屏。
- `components/ui/` *放可复用组件*：按钮、卡片、标签这类会在多处出现的东西集中管理，避免同一个按钮在三个地方各写一遍。
- `animations/` *抽离动画逻辑*：时间轴编排和滚动触发配置往往比组件本身还长，混在组件里会让组件文件迅速膨胀。抽出来后组件里只剩一行绑定。
- *单组件超 250 行必须拆*：给"太大了"一个客观标准，不靠感觉判断。
- *导入用* `@/` *别名*：避免 `../../../components` 这种路径，移动文件时不用改一堆导入。

**规则文件全文**

```
---
description: 项目架构与代码组织规范（目录职责、拆分规则）
alwaysApply: true
---

# 项目架构规范

框架：Next.js App Router，源码统一放在 `src/` 下。

## 目录职责

src/
  app/          # 路由与页面：page.tsx / layout.tsx，只做组合
  sections/     # 页面区块：首屏、档案列表等成块的页面内容
  components/   # 可复用组件
    ui/         # 通用 UI 组件（按钮、卡片、标签等）
    providers/  # 全局 Provider（如 SmoothScrollProvider）
  animations/   # 动画逻辑：GSAP 时间轴、ScrollTrigger 配置、动画工具
  hooks/        # 自定义 React hooks
  lib/          # 工具函数、常量、类型

## 组织规则

- `page.tsx` 只负责组合 sections，不写具体布局和动画逻辑，严禁巨型 page 文件。
- 页面区块放 `sections/`，一个区块一个文件。
- 动画逻辑（时间轴编排、ScrollTrigger 配置）抽离到 `animations/`，组件内只做绑定。
- 可复用 UI 放 `components/ui/`，不在 sections 里重复实现。
- 单个组件超过 250 行必须拆分。
- 导入一律使用 `@/` 别名（如 `@/sections/hero`），不用相对路径跨目录。
```

**三阶段怎么用**

- 前期：建项目时就把目录骨架建齐（哪怕是空文件夹），让 AI 一开始就有地方可放。
- 中期：每新增一屏先建 `sections/` 文件；发现某个组件变胖立刻拆，不要攒着。
- 后期：清理未引用的组件和素材，保持目录与实际使用一致。

### 规则 3：代码质量（code-quality.mdc）

**它解决什么问题**

AI 写代码时为了让类型检查通过，很容易滥用 `any`；调试时加的 `console.log` 忘了删；改需求后留下一堆不再使用的导入。这些单看都是小问题，积累起来会让代码库难以维护。

**逐条解释**

- *TypeScript 严格模式不得关闭*：类型检查是 AI 协作最有效的安全网，它能在编译期拦住大量低级错误。
- *禁止* `any`*，未知类型用* `unknown` *收窄*：`any` 会让类型检查在这一点完全失效，等于开了个洞。
- *禁止* `console.log`*，但允许* `console.warn` */* `console.error`：区分"调试残留"和"真实错误处理"，不搞一刀切。
- *禁止未使用的导入和变量*：它们通常是重构留下的垃圾，也可能暗示某段逻辑没写完。
- *组件命名见名知义*：禁止 `Comp1`、`Test`、`Temp` 这类占位名——AI 起临时名字后往往不会回来改。
- *新建前先查重*：AI 不主动搜索时会重复造轮子，明确要求它先找现有实现。
- *前四条由 ESLint 强制，不许用* `eslint-disable` *绕过*：把约束落到工具上，规则文件负责解释原因。堵死绕过的口子很重要，否则 AI 遇到报错的第一反应就是加注释关掉检查。

**规则文件全文**

```
---
description: 代码质量规范（TypeScript 严格模式、命名、去重）
alwaysApply: true
---

# 代码质量规范

- TypeScript 严格模式（`tsconfig.json` 已开启 `strict: true`，不得关闭）。
- 禁止 `any`（含隐式 any）；类型未知时用 `unknown` 收窄。
- 禁止 `console.log`；调试代码提交前必须删除（`console.warn` / `console.error` 允许用于真实错误处理）。
- 禁止未使用的导入和变量。
- 提交前 `npm run lint` 必须零错误通过。
- 组件命名必须有意义、见名知义（如 `ArchiveCard`、`HeroIntro`），禁止 `Comp1`、`Test`、`Temp` 之类名称。
- 新建组件前先检查 `components/` 与 `sections/` 是否已有同功能实现，避免重复组件；相似度高的组件应抽象合并。

以上前四条已由 ESLint 强制（见 `eslint.config.mjs`），报错必须修复，不允许用 `eslint-disable` 绕过。
```

**三阶段怎么用**

- 前期：配好 `tsconfig` 的 `strict: true` 与 ESLint 规则并锁死，同时写下这份规则解释为什么。
- 中期：每次提交前跑 `npm run lint`，零错误才提交。
- 后期：把 lint + build 全量通过作为上线门槛。

### 规则 4：设计令牌（design-tokens.mdc）

**它解决什么问题**

没有令牌约束时，AI 会自由发挥：颜色写 `#3ECA57`（和设计稿差一点）、间距写 `gap-[13px]`、字号写 `text-[17px]`。页面看着能用，但和设计稿永远对不齐，且同类元素之间毫无一致性。

令牌的核心思想是**把可用值限定成有限的几档**，颜色只有这十个、字号只有这十七档、间距只有这二十四档。选择变少了，一致性自然就有了。

**逐条解释**

- *以 Figma 导出的 JSON 为唯一事实来源*：设计师改了值，先更新 JSON，再同步代码和文档。"三处一致"是这套机制能长期成立的前提。
- *颜色只用给定色板*：明确禁止 Tailwind 默认调色板和任意十六进制值。Tailwind 自带的 `gray-500` 之类很容易被顺手用上，必须点名禁止。
- *字体族与字重分别限定*：中文衬线字体通常没有粗体和斜体变体，强行用会触发浏览器合成字形，效果很糟。规则里要写清每款字体可用哪几档字重。
- *字号、行高、间距、圆角给出完整刻度*：列出所有可用值，并说明对应的 Tailwind 写法，AI 才能准确使用。
- *缩放例外条款*：桌面端需要随视口放大时可以写 `calc(var(--su) * N)`，但 N 仍必须取自刻度。这条是为了兼容下一份规则的缩放机制，既允许缩放又守住刻度体系。
- *更新流程*：明确"JSON → CSS 变量 → 规则文档"三处同步，防止时间一长三者各说各话。

**规则文件全文**（色值与刻度请替换为你自己项目的设计系统）

```
---
description: 网站设计令牌（颜色、字体、字号、行高、间距、圆角）使用规范
alwaysApply: true
---

# 设计令牌规范

令牌源文件：`design/tokens/*.tokens.json`（Figma 变量导出，为唯一事实来源）。
CSS 变量定义在 `src/app/globals.css` 的 `@theme` 块中，样式一律使用令牌值，不要使用刻度外的任意值。

例外：桌面态尺寸需随视口等比缩放时，写成 `calc(var(--su) * N)`，其中 `N` 仍必须取自下列刻度——倍率只放大稿面尺寸，不新增刻度值。缩放机制见 `responsive-layout` 的「内容缩放」一节。

当前集合：`color`、`font-family`、`font-size`、`font-weight`、`line-height`、`radius`、`spacing`。

## 颜色（Color）

- Grey（中性灰）：`grey-50` ~ `grey-400` + `white`
  - 50 #F4F4F4 / 100 #DEDEDE / 200 #999999 / 300 #666666 / 400 #131313 / White #FFFFFF
- Tailwind 用法：`text-grey-300`、`bg-grey-400`、`border-grey-100` 等。
- 只使用以上色板，不使用 Tailwind 默认调色板或任意 hex 值。

## 字体（Typography）

- 字体族（FontFamily）：`Noto Serif SC`（中文衬线，主字体）、`Libre Bodoni`（西文衬线，标题/装饰）。
  - Tailwind：`font-serif-sc`、`font-bodoni`。
- 字号刻度（FontSize，px）：10 / 12 / 14 / 16 / 18 / 20 / 24 / 28 / 32 / 36 / 40 / 44 / 48 / 52 / 56 / 60 / 100。
  - Tailwind：`text-10` ~ `text-60`、`text-100`；桌面态随视口缩放时用 `text-[length:calc(var(--su)*N)]`。
- 行高刻度（LineHeight，px）：14 / 18 / 20 / 24 / 26 / 28 / 32 / 36 / 40 / 44 / 48 / 52 / 56 / 60 / 64 / 68，用 `leading-[Npx]` 或与字号配对；随视口缩放时用 `leading-[calc(var(--su)*N)]`。
- 字重（FontWeight）：Regular 400、Medium 500、SemiBold 600。
  - Noto Serif SC：仅 Light 300、Regular 400、Medium 500 三档，禁止 SemiBold / 其他字重。
  - Libre Bodoni：Regular 400、Medium 500、SemiBold 600 三档（如 `font-semibold`）。
  - 斜体不是字重：需要斜体时对 Libre Bodoni 用 CSS `italic`；Noto Serif SC 无斜体变体，不对中文使用 `italic`。

## 间距（Spacing）

扁平刻度，单位 px，用于 gap、padding、margin、段落间距：

0 / 2 / 4 / 6 / 8 / 10 / 12 / 16 / 20 / 24 / 28 / 32 / 36 / 40 / 44 / 48 / 52 / 56 / 60 / 64 / 68 / 72 / 76 / 80

Tailwind 默认 4px 基数刻度可直接映射（如 `gap-5` = 20px、`p-10` = 40px）；6px 用 `p-1.5`、10px 用 `p-2.5`。不使用刻度以外的间距值；桌面态随视口缩放时写 `gap-[calc(var(--su)*20)]` 这类形式，括号内仍取本刻度。

## 圆角（Radius）

- RS（小）：2 / 4 / 8 → `rounded-rs-2` / `rounded-rs-4` / `rounded-rs-8`
- RM（中）：12 / 16 / 20 → `rounded-rm-12` / `rounded-rm-16` / `rounded-rm-20`
- RL（大）：24 / 28 / 32 → `rounded-rl-24` / `rounded-rl-28` / `rounded-rl-32`

## 更新流程

设计令牌变更时：先替换 `design/tokens/` 下对应 JSON，再同步 `globals.css` 的 `@theme` 变量与本规则，保持三处一致。
```

**三阶段怎么用**

- 前期：从 Figma 导出令牌 JSON，在 `globals.css` 的 `@theme` 里定义对应 CSS 变量，把刻度抄进规则文档，三处对齐后再开始写页面。
- 中期：所有样式只取刻度值；设计改稿时走更新流程，先换 JSON。
- 后期：逐项复查三处是否仍然一致（颜色、字号、行高、间距、圆角），这是很容易在长期迭代中悄悄走样的地方。

### 规则 5：响应式布局（responsive-layout.mdc）

**它解决什么问题**

设计稿通常只给一个宽度（比如 1440），但用户的屏幕从 1280 到 3840 都有。这份规则回答两个问题：**框怎么变**（页边距、栅格）和**框里的内容怎么变**（字号、间距、元素尺寸）。

这是最容易被前期忽略、后期代价最大的一份规则。一个真实教训：某项目首版规则写的是"页面边距固定 30px，所有分辨率下恒定不变"，并且完全没规定内容缩放策略。结果在 2560、3440 这类宽屏上，内容挤在中间一小块、四周大片空白，视觉上极其失衡。最终边距规则被整个推翻改成自适应，内容缩放机制则是在项目后期临时补的，光是调试缩放倍率就单日返工十余次。

**所以请在前期就对着你的最大目标分辨率想清楚：超宽屏上，你希望内容跟着放大，还是维持原尺寸留白？**

**逐条解释**

*布局基线部分*

- *页边距随视口增宽*：用 `clamp(20px, calc(100vw / 72), 40px)`，意思是最小 20px、最大 40px，中间按视口宽度的 1/72 线性变化。这样小屏不浪费空间，大屏不显局促。
- *边缘 UI 一律用变量定位，禁止写死*：导航、滚动提示这类贴边元素如果写死像素，改边距策略时会漏掉一堆。
- *全屏媒体不受边距约束*：背景图、视频要边到边铺满，这是例外。

*栅格部分*

- *8 列栅格、gutter 恒定 20px*：列数和列间距固定，只有列宽随视口变化。gutter 不缩放是刻意的——间距跟着放大会让大屏显得松散。
- *新增区块先按列规划再落像素*：强制先想结构再想细节。

*内容缩放部分（核心）*

- 定义两个倍率：`--su` 是 `min(100vw, 1680px) / 1440`，即以 1440 稿面为基准，视口越宽越放大，到 1680 封顶（最大 1.17 倍）；`--su-hero` 封顶 1920（最大 1.33 倍）。
- *为什么要封顶*：不封顶的话 3840 屏上字号会变成 2.67 倍，大到荒谬。封顶后超出部分作为留白。
- *为什么要两套*：正文放大 1.17 倍就够了，再大显得笨重；但大标题和主图作为视觉主角，放大 1.33 倍才有气势。一套倍率无法同时满足，所以拆成默认档和主角档。
- `--su-hero` *严格限定使用范围*：明确只给大标题和主图用，防止它逐渐蔓延到全站，让两套倍率失去区分意义。
- *右列宽联动*：如果站内多个区块要对齐同一条竖线，把这个宽度写成规则并列出所有使用处，改一处时才知道要同步哪些。
- *写法要求写* `calc(var(--su) * N)` *而非预先算好*：保留原始稿面数值，后来者一眼能看出"设计稿上这里是 24px"。
- *装饰性对位值例外*：旋转文字的行高、贴图内的坐标这类对稿实测值，按原值写，不强行归到刻度。
- *移动端禁用倍率*：手机视口下倍率会被压到 0.3 以下，文字完全不可读。移动端必须用独立设计稿和独立布局。
- *JS 换算必须与 CSS 同封顶值*：有些定位要在 JS 里实测文字宽度后计算，两边封顶值不一致会错位。

*测试分辨率部分*

- 列出必测清单，覆盖常见桌面、平板、手机尺寸。没有清单时，测试往往只在开发者自己那块屏幕上进行。
- *不要自行推断未提供的断点布局*：这条是给 AI 的——没有移动端设计稿时，让它按桌面稿瞎猜出来的移动端布局通常很糟，不如先不做。

# 响应式布局规范

## 布局基线

- 页面四周边距随视口增宽：`--page-margin: clamp(20px, calc(100vw / 72), 40px)`（1440 及以下 20px，1920≈26.7px，2560≈35.6px，2880 起封顶 40px）。
- 边缘锚定的 UI（导航、语言切换、滚动提示、页角信息等）一律用 `var(--page-margin)` 定位，禁止写死 20px。
- 推荐容器写法：`width: calc(100% - var(--page-margin) * 2)`，居中；上下用 `top/bottom: var(--page-margin)`。
- CSS 变量定义见 `globals.css`。
- 正文内容块（段落、卡片栅格）如需限宽提升可读性，可另行设置 `max-width` 并居中，但不影响边缘 UI 的边距定位。
- 全屏媒体（背景图、视频）边到边铺满，不受页边距约束。

## 栅格系统

- 8 列栅格（Columns = 8）。
- 列间距（Gutter）：20px，恒定，不随分辨率变化。
- 版心宽度：`100% - 2 × var(--page-margin)`。
- 单列宽计算：`(版心宽度 - 7 × 20px) / 8`。
- 内容对齐优先落在列线或跨列；新增区块先按 8 列规划，再落到具体像素。

## 内容缩放（--su / --su-hero）

桌面设计稿基准 1440 宽。边距和栅格管的是「框」，框里的字号、行高、间距、元素尺寸由两个缩放倍率控制，定义见 `globals.css`：

--su:      calc(min(100vw, 1680px) / 1440);   /* 1680 封顶，最大约 1.17 倍 */
--su-hero: calc(min(100vw, 1920px) / 1440);   /* 1920 封顶，最大约 1.33 倍 */

### 适用范围

- `--su`（默认）：桌面态一切按稿面走的尺寸——正文与标签字号、行高、gap/padding、图标与方块尺寸、导航 tab 间距等。拿不准用哪个时一律用 `--su`。
- `--su-hero`（例外，仅视觉主角）：首屏大标题，以及主图媒体块。除此之外不得扩大 `--su-hero` 的使用面。
- 右列宽 507：导航右栏、联系页服务范围、组织记录铭牌、作品圆环行都以 `calc(var(--su-hero) * 507)` 推导左缘或宽度，保持全站右列同一条竖线。改动其中任何一处都要同步其余几处。

### 写法

- 稿面像素一律写成 `calc(var(--su) * N)`，其中 `N` 取设计稿上的原始像素值，不要预先算好结果再写死。
- 字号用 `text-[length:calc(var(--su)*N)]`，行高用 `leading-[calc(var(--su)*N)]`。
- 倍率只缩放尺寸，不改变令牌刻度：`N` 必须仍取自 `design-tokens` 的字号 / 行高 / 间距刻度。例外：对稿实测的装饰性对位值（如旋转文字的行高、贴图内的坐标尺寸）按稿面原值书写，不强行归到刻度。
- 边距用 `var(--page-margin)`，不要用 `--su` 推导页边距；gutter 恒定 20px，同样不缩放。

### 边界

- 倍率是桌面态（≥768px）机制。移动端有独立设计稿与布局，禁止在移动端样式里使用 `--su` / `--su-hero`（小视口会把倍率压到 0.3 以下，文字将不可读）。
- JS 里需要同等换算时（如实测文字宽度后定位），必须与 CSS 用同一封顶值：`Math.min(window.innerWidth, 1680) / 1440`、`Math.min(window.innerWidth, 1920) / 1440`。
- 调整封顶值会整体改变大屏观感，属于全站级变更，须先确认再改，并同步更新本节数值与注释。

## 测试分辨率

- 桌面端：1280×800、1440×900、1920×1080、2560×1440、3440×1440、3840×2160
- 平板：768×1024
- 移动端：375×812、390×844、412×915

- 避免固定像素动画距离，优先百分比、视口单位、`clamp()`；位移需与稿面尺寸挂钩时，乘上同一套 `--su` 倍率，不要写死像素。
- 大屏使用 `gsap.matchMedia()` 调整 GSAP 时间轴。
- 在不同视口高度下检查 ScrollTrigger 的 pin 时长与触发点。
```

### 规则 6：GSAP + Lenis 动画集成（gsap-lenis-integration.mdc）

**它解决什么问题**

动画库的接线方式如果不统一，会出现各种诡异问题：多个平滑滚动实例互相打架、滚动动画抖动错位、页面刷新瞬间元素闪一下再归位。这份规则把接线方式固定下来。

**先理解两个库的分工**：GSAP 是动画引擎，负责"元素怎么动"（把 transform、opacity 从 A 变到 B，提供时间轴和滚动触发器）；Lenis 是平滑滚动库，负责"页面怎么滚"（拦截滚轮输入，用惯性插值代替浏览器的直接跳转，产生带阻尼的丝滑手感）。链条是：输入 → Lenis 算滚动位置 → ScrollTrigger 感知 → GSAP 驱动元素。

**逐条解释**

- *全局唯一 Lenis 实例*：多个实例会争抢滚动控制权，必须在一个 Provider 里创建，全站共用。
- `autoRaf: false`*，由* `gsap.ticker` *驱动*：两个库各自跑一套动画帧循环会导致不同步（滚动位置和动画进度差一帧）。统一由 GSAP 的心跳驱动，两者永远同帧。
- *Lenis 的 scroll 事件必须同步* `ScrollTrigger.update`：不加这行，滚动触发的动画会抖动或错位。这是最容易漏的一步。
- `gsap.ticker.lagSmoothing(0)`：关闭 GSAP 的掉帧补偿，避免卡顿后动画突然跳跃。
- *动画组件必须标* `"use client"`：动画依赖浏览器 API，服务端渲染不了。
- *用* `useGSAP({ scope })` *而非手写* `useEffect`：`useGSAP` 会自动清理动画实例，手写清理很容易遗漏，导致组件卸载后动画还在跑。
- *用* `data-`* *属性选择动画目标*：类名可能因为样式调整而改变，`data-reveal-card` 这类专用属性更稳定，且一眼能看出这个元素参与动画。
- *初始隐藏状态用 CSS 类预设*：否则服务端渲染出来的元素会先以最终状态闪现一下，再被 JS 设回初始态。
- *所有动画用* `gsap.matchMedia()` *区分 reduced-motion*：这是无障碍的硬要求，见规则 8。

### 规则 7：性能（performance.mdc）

**它解决什么问题**

网站"卡"通常来自三个地方：动画触发了浏览器重排、动画值走 React state 导致每帧重渲染、图片视频没优化。这份规则针对性地划三条红线。

**逐条解释**

*动画性能*

- *只对 transform 和 opacity 做动画*：这两个属性可以由 GPU 直接合成，不需要浏览器重新计算布局。动 width、top、margin 会触发重排（reflow），每帧都要重算整个页面的布局，在复杂页面上必卡。
- *需要尺寸变化用* `scale` *或 clip-path 替代*：给出替代方案，否则规则无法执行。
- *动画值不放 React state*：用 `useState` 存鼠标坐标或滚动进度，意味着每帧都触发一次 React 重渲染，开销巨大。正确做法是用 GSAP 的 `quickTo` / `quickSetter` 直接改 DOM，或存在 `useRef` 里。

*图片与媒体*

- *一律用* `next/image`：它自动处理格式转换、响应式尺寸、懒加载。裸 `<img>` 什么都没有。
- *首屏图片加* `priority`*，首屏以下懒加载*：首屏图要抢先加载，下面的图等滚到了再加载。
- *提供* `sizes` *属性*：不给的话大屏可能下载远超所需尺寸的图片。
- *素材入库前压缩*：这是最简单也最有效的优化。照片转 AVIF/WebP，视频压码率，往往能减掉 70% 以上体积。

*客户端组件*

- *默认 Server Component*：只有需要交互、动画或浏览器 API 的组件才加 `"use client"`。
- `"use client"` *下沉到叶子*：标在页面或布局层，会让整棵子树都变成客户端组件，白白增加 JS 体积。

# 性能规范

## 动画性能

- 只对 `transform`（x/y/scale/rotate）和 `opacity` 做动画，它们不触发重排且可由 GPU 合成。
- 禁止对布局属性做动画：`width`、`height`、`top`、`left`、`margin`、`padding`、`font-size` 等。

- 图片一律使用 `next/image`，禁止裸 `<img>` 标签。
- 首屏关键图片加 `priority`；首屏以下的图片和视频懒加载（`next/image` 默认懒加载，视频用 `preload="none"` + 进入视口再播放）。

### 规则 8：无障碍（accessibility.mdc）

**它解决什么问题**

无障碍最大的特点是：**后期补的成本是前期做的十倍以上**。因为它不是某个模块的功能，而是散布在每一个交互元素上。等站做完了再来补键盘导航和焦点样式，等于把所有组件重看一遍。

**逐条解释**

- *所有动画响应* `prefers-reduced-motion`：部分用户会因前庭功能障碍在大量动效下产生眩晕，操作系统提供了"减少动态效果"开关，网站必须尊重它。reduce 时不是不显示内容，而是直接呈现动画的最终状态。
- *键盘导航*：所有交互元素必须能 Tab 到达、能 Enter/Space 触发。自定义交互组件要补 `tabIndex` 和键盘事件处理。
- *禁止* `outline: none` *而不提供替代*：这是最常见的无障碍破坏行为——为了美观去掉焦点框，键盘用户就完全不知道自己在哪。正确做法是用 `focus-visible:` 做一个符合设计风格的焦点样式。
- *图片 alt*：内容图写有意义的描述，装饰图写 `alt=""`（空字符串告诉读屏软件跳过它，而不是念出文件名）。
- *语义化标签*：点击行为用 `<button>`，页面跳转用 `<a>` / `<Link>`。给 `<div>` 加 onClick 是 AI 的常见偷懒做法，这样的元素键盘完全不可达。
- *hover 效果只作增强*：核心信息和操作不能只能通过悬停获取，因为触摸设备没有 hover 状态。

# 无障碍规范

- 减少动态效果：所有动画必须响应 `prefers-reduced-motion`（GSAP 用 `gsap.matchMedia()` 区分，reduce 时直接呈现最终状态；平滑滚动由 `SmoothScrollProvider` 自动降级）。
- 键盘导航：所有交互元素（链接、按钮、卡片）必须可 Tab 到达、可 Enter/Space 触发；自定义交互组件补 `tabIndex` 和键盘事件；禁止 `outline: none` 而不提供替代焦点样式。
- 焦点状态：交互元素必须有可见焦点样式，用 `focus-visible:` 实现（如 `focus-visible:ring-2`），风格与设计系统一致。
- 图片 alt：内容图片必须写有意义的 `alt`；纯装饰图片用 `alt=""`。
- 语义化标签：可点击行为用 `<button>`，页面跳转用 `<a>`（Next.js 用 `<Link>`）；禁止给 `<div>` 加 onClick 充当按钮。
- 鼠标跟随/悬停类效果只作为增强，核心信息和操作不得只能通过 hover 获取。
```

**三阶段怎么用**

- 前期：定标准，并在公共组件（按钮、导航、卡片）里先把焦点样式和键盘事件做出来，后面复用就自动合规。
- 中期：每个新交互组件自带键盘支持和焦点样式，不留欠账。
- 后期：打开系统的"减少动态效果"开关过一遍全站，再用纯键盘（不碰鼠标）操作一遍所有核心流程。

## 五、后期：收敛与上线前必须执行的规则

### 规则 9：浏览器兼容与分端（browser-compat.mdc）

**它解决什么问题**

这份规则回答一个很多人踩过的坑：**在 Chrome 上做得好好的网站，到了 Safari 和手机上全是问题**。

原因在于 Chrome 对各种前沿特性的支持最激进、性能最好，而 Safari（以及所有 iOS 浏览器）在 WebGL、backdrop-filter、Canvas 批量绘制、视频编码上都有明显短板。如果整个开发期只在 Chrome 里验证，兼容问题会在上线前集中爆发——这正是真实项目里发生过的事：上线前两周几乎全部时间都在修 Safari，某个雾玻璃效果修了五天最终还是选择在 Safari 上整个关掉。

**虽然这份规则的完整执行在后期，但其中的降级思路必须在中期写效果时就贯彻。**

**逐条解释**

*支持基线*

- 明确写出 browserslist 目标（Chrome ≥ 100、Safari ≥ 15 等）并要求不得收窄。有过教训：某次构建输出了 Safari 15 不支持的新语法，导致整页无法滑动，排查了很久才定位到是语法降级配置问题。

*判端与分包*

- *判端统一用一个 hook*：满项目散落 `matchMedia` 和 UA 嗅探，逻辑会逐渐不一致。统一到一处，SSR 时默认按移动端返回，避免手机下载桌面专属的重型代码包。
- *重资源按端拆分*：WebGL 效果、桌面视频、大图这类东西，手机不该下载。
- *iOS 上所有浏览器都是 WebKit*：这是最容易漏的知识点——iPhone 上的 Chrome、Firefox、Edge 内核全是 WebKit（苹果政策要求），所以判断"要不要用 Safari 的方案"时，条件是 `iOS 或 Safari`，而不是只判 Safari。

*视频*

- *透明视频必须双源*：带 alpha 通道的视频，Chrome 系用 VP9 WebM，Safari 和 iOS 必须用 HEVC MP4。WebKit 不支持 VP9 alpha，只给 WebM 的话会渲染成黑底而不是透明。
- *下载进度用 XHR + blob*：`<video>` 标签的 progress 事件在 Safari 下不稳定，曾导致加载进度永远卡在 0%。改用 XHR 请求视频、监听它的 onprogress，全浏览器表现一致。
- *首屏以下视频* `preload="none"`：避免一进页面就并发下载几十兆视频。

*Safari 重效果降级（这是全篇最重要的部分）*

- *backdrop-filter + mask*：Safari 每次更换 mask 或改 transform 都会把整层重新采样，视觉上就是闪烁。缓解手段有一套组合拳：限制 mask 更新频率、mask 用 1 倍分辨率而非设备像素比、用 left/top 定位代替 transform、位置取整避免亚像素抖动、用 blob URL 代替 data URL。如果这些都不够，就整段降级。
- *WebGL*：Safari 下关闭多重采样抗锯齿（MSAA）、压低像素比；画布输出要与合成层的预乘 alpha 约定一致，否则光斑边缘会出现一圈外框。最重要的一条是渲染循环必须"静止即停帧"——没有变化时就不要继续请求动画帧，否则 Safari 会持续满载 GPU，风扇狂转。
- *Canvas 2D 大批量绘制*：Chrome 的 Skia 引擎能把上万次 drawImage 合批，Safari 不能。整屏字符、粒子这类绘制必须预先构建好，并按时间预算分帧执行，否则会长时间阻塞主线程。
- *图片 mask 换帧*：Safari 图片解码是异步的，帧还没解码完就切换会闪一帧全遮罩。要等解码完成再切。
- *降级原则*：症状明确但修不动时，果断按浏览器分支关掉效果、退化成静态或 hover 触发。**不要无限调参**——这条是用五天时间换来的经验。

*移动端布局与滚动*

- *可滚区域必须放开滚动拦截*：平滑滚动库和全局触控处理会吃掉 touchmove 事件，导致页面内的弹窗、抽屉、列表在 iOS 上完全滚不动。这类容器要挂豁免属性。
- *手机上用确定性布局*：在高度不确定的手机视口里，"图片自适应收缩"和"弹性间隔"两种方案都试过并失败了——前者会裁切图片，后者让按钮位置飘忽。最终采用"固定间距 + 正文区内部滚动 + 操作按钮固定在底部工具条"，这是唯一稳定的方案。
- *移动端禁用桌面缩放倍率*：见规则 5。

*提测要求*

- 明确写死：涉及视频、WebGL、backdrop-filter、Canvas、滚动交互的改动，合入前必须在 macOS Safari 与 iOS Safari 各过一遍，只在 Chrome 验证不算通过。把它写成规则，才不会在赶进度时被跳过。

**规则文件全文**

```
---
description: 浏览器兼容与分端规范（Safari/WebKit、移动端、重效果降级）

# 浏览器兼容与分端规范

支持基线（`package.json` 的 browserslist）：Chrome ≥ 100、Safari ≥ 15、Firefox ≥ 100、Edge ≥ 100。不要收窄；输出语法必须兼容 Safari 15（曾因新语法导致 Safari 15 整页无法滑动）。

## 判端与分包

- 判断桌面/移动一律用 `@/hooks/use-desktop-media`（`min-width: 768px`，SSR 按移动端返回 false），不要另写 `matchMedia` 或 UA 嗅探判端。
- 重资源（WebGL 效果、桌面视频、大图）按端拆分加载：移动端不得下载桌面分包，反之亦然。
- 判 WebKit（选视频编码等）：iOS 上所有浏览器（含 iPhone Chrome）都是 WebKit，按 Safari 处理。

## 视频

- 透明（alpha）视频必须双源：VP9 WebM（Chrome/Firefox/Edge）+ HEVC alpha MP4（Safari 与全部 iOS 浏览器）。WebKit 不支持 VP9 alpha，只给 WebM 会黑底。
- 需要真实下载进度的预载用 XHR + blob，不要依赖 `<video>` 的 `progress` 事件——Safari 下不稳定，曾导致加载卡死在 0%。
- 首屏以下视频 `preload="none"`，进入视口再加载；手机端提供更低码率的独立文件。

## Safari 重效果降级（必须）

新增或改动以下类型的效果时，必须在 Safari 实测，且预留降级路径：

- backdrop-filter + mask：Safari 每次换 mask / 改 transform 会整层重采样闪烁。对策：限制 mask 更新频率、mask 用 1× 分辨率、用 `left/top` 而非 `transform` 定位、位置取整、用 blob URL 而非 data:URL。仍不可接受时整段降级。
- WebGL：Safari 下关 MSAA、压像素比；画布输出与合成层保持预乘 alpha 一致，否则光斑/边缘出现外框。渲染循环必须"静止即停帧"，禁止空转 rAF——Safari 曾因此持续 GPU 满载。
- Canvas 2D 大批量绘制：Safari 无法像 Chrome（Skia）那样合批上万次 drawImage，整屏字形/粒子类绘制要预构建 + 分帧（按时间预算切片）。
- 图片 mask 换帧：Safari 异步解码，帧未就绪就换会闪一帧全遮，先解码完成再切。

降级原则：症状明确修不动时，果断按 `isSafari` 分支关掉效果、退化为静态或 hover 触发，不要无限调参。

## 移动端布局与滚动

- iOS Safari 页面内可滚区域会被平滑滚动库 / 全局触控拦截吃掉事件：移动端区块需要原生滚动时，必须放开拦截（Lenis 用 `data-lenis-prevent`，并检查 `touch-action`）。
- 高度不定的手机视口里，"大图自适应收缩"和"弹性间隔"都验证失败过；采用固定间距 + 正文区内部滚动 + 操作按钮固定在底部工具条的确定性布局。
- 移动端禁止使用 `--su` / `--su-hero`（见 responsive-layout 规则），按对应设计稿画板实现。

## 提测要求

涉及视频、WebGL、backdrop-filter、Canvas、滚动交互的改动，合入前至少在 macOS Safari 与 iOS Safari（真机或模拟器）各过一遍；只在 Chrome 验证不算通过。
```

**三阶段怎么用**

- 前期：定 browserslist 基线并确认构建的语法降级目标；规划分端加载策略，把判端 hook 先写出来。
- 中期：**写重效果的同时就留降级分支**，不要想着"先做出效果，兼容以后再说"。每做完一个视觉效果，顺手在 Safari 里开一次，五分钟的事，能省掉后期几天。
- 后期：按提测要求全量过 macOS Safari 和 iOS Safari；对确实修不动的效果执行降级决策。

## 七、给新项目的六条经验

1. **前期规则宁多勿少，但每条都要能执行**。"代码要优雅"不是规则，"单组件超 250 行必须拆"才是。
2. **响应式策略是最容易低估的一项**。开工前就对着最大目标分辨率想清楚：超宽屏上内容是跟着放大还是留白？想不清楚就先做一个最宽分辨率的设计稿。
3. **不要只在 Chrome 里开发**。至少每完成一个视觉效果就在 Safari 里看一眼，成本极低，收益极高。
4. **能自动化的约束一定要自动化**。ESLint 能管的别只写在文档里，人和 AI 都会忘，工具不会。
5. **规则是活的，要随实践修订**。发现规则与实际做法冲突时，要么改代码要么改规则，不能放任两者不一致——规则一旦失真，AI 就会继续按错误的描述工作。
6. **降级不丢人**。某个效果在特定浏览器上修不动，果断关掉它、换个简单实现，比无限调参明智得多。用户感知不到"这里本来有个很酷的效果"，但一定感知得到页面卡顿。
